# 🏛️ 아키텍처 FAQ

---
## 🤔 "Facade가 단순히 내부 서비스를 1:1로 감싸는 것 아닌지에 대해서..."

저희 프로젝트의 구조를 처음 접하면 "Facade 메서드가 결국 내부 서비스의 메서드 하나를 그대로 호출하는 것뿐인데, 굳이 이렇게 한 단계를 더 두는 것이 과한 것 아닌가?" 라는 의문이 들 수 있습니다.

이는 Facade가 수행하는 역할을 단편적으로 본 것입니다. 저희 프로젝트의 Facade는 단순히 **내부 서비스의 기능을 외부에 그대로 노출하는 역할**뿐만 아니라, 여러 서비스와 로직을 엮어 **복잡한 유스케이스를 단일 기능으로 통합하여 제공하는 역할**까지 수행합니다. 이 두 가지 역할 모두 저희 아키텍처의 핵심입니다.

---

### 1. 내부 기능 노출 (Simple Delegation)

단순한 조회 기능의 경우, Facade는 내부 서비스를 1:1로 호출하는 것이 맞습니다.

* **예시**: `BookQueryFacade.getBookBasicInfoForShare(bookId)`

그러나 이러한 단순 1대1 연결 호출조차도, **"책의 기본 정보가 필요하면 BookQueryFacade의 .getBookBasicInfoForShare() 메소드만 호출하면 된다는 의미. 내부에 DB가 있든, 외부 API 호출이 있든 이 메소드를 사용하는 쪽은 알 필요가 없다."** 는 명확한 경계를 설정해주는 매우 중요한 역할을 합니다. 즉, 도메인의 자율성을 보장하고 내부 구현을 완벽하게 숨기는 가장 기본적인 책임을 다하는 것입니다.


---

### 2. 복합 유스케이스 통합 (Orchestration)

하지만 복잡한 요구사항이 등장하면 Facade 패턴의 힘이 드러납니다. 이때 Facade는 여러 내부 서비스와 리포지토리를 조합하여 하나의 의미 있는 결과를 만들어냅니다.

* **예시**: `ClubQueryFacade.getHomeFeedForShare(memberId, size)`

외부에서는 이 단 하나의 메서드를 호출했을 뿐이지만, Facade의 내부 구현체는 다음과 같은 복잡한 과정을 처리해서 제공하게 됩니다.

1.  `memberId`로 가입한 모든 클럽 ID를 조회하고,
2.  각 클럽의 최신 공지(`Notice`)와 투표(`Vote`)를 각각 가져와,
3.  이들을 하나의 리스트로 통합한 뒤,
4.  전체 리스트를 생성 시간(`createdAt`) 기준으로 다시 정렬하고,
5.  요청한 `size` 만큼 잘라내어,
6.  최종적으로 외부 공유용 DTO(`ClubUpdatePreviewDTO`)로 변환하여 반환합니다.

하지만 외부에서 이 메소드를 호출하게 되는 도메인은 이 모든 복잡성을 전혀 알 필요 없이, Facade가 제공하는 단 하나의 메서드만 호출하면 됩니다.

---
### 💡 결론

> Facade에 1:1 매핑처럼 보이는 단순한 메서드와 여러 로직을 조합하는 복잡한 메서드가 공존하는 것은, 이 아키텍처가 다양한 복잡도의 요구사항을 유연하게 처리하고 있다는 **건강한 신호**입니다.

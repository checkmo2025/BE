# 🏛️ 아키텍처 설계: Facade 패턴

---
## 1. 왜 Facade 패턴인가?

저희는 기존에 단일 서버 환경의 **모놀리식(Monolithic) 아키텍처**로 프로젝트를 개발해왔습니다. 이 과정에서 대규모 서비스에 널리 사용되는 **마이크로서비스 아키텍처(MSA)**의 장점에 주목하게 되었습니다.

그러나 **MSA**로의 완전한 전환은 상당한 복잡성을 동반하기에, 저희는 현실적인 대안을 모색했습니다. 바로 **모놀리식 아키텍처의 안정성을 유지하면서, 그 내부에 MSA의 핵심 장점인 '도메인 간의 낮은 결합도'를 구현**하는 것이었습니다.

이 목표를 달성하기 위한 핵심 설계 패턴으로 **Facade 패턴**을 도입했으며, 각 도메인은 오직 Facade를 통해서만 소통하는 것을 원칙으로 삼았습니다.

### 🧱 패키지 구조의 변경

저희는 기존에 `service`, `entity`, `repository`와 같이 계층을 기준으로 패키지를 구성하는 전형적인 레이어드 아키텍처(Layered Architecture)를 사용해왔습니다. 그러나 저희는 **대규모 서비스의 확장성과 유지보수성을 확보하는 MSA 설계를 학습하고 프로젝트에 적용해보고자 하는 기술적인 목표**를 세웠습니다.

이 목표를 달성하기 위해, 저희는 **패키지 구조를 기능 중심의 도메인(Domain) 기준으로 설계**했습니다. 그리고 **"각 도메인은 자신의 경계 밖을 절대 직접 참조할 수 없다"** 는 핵심적인 팀 규칙을 세웠습니다. 다른 도메인의 정보나 기능이 필요할 경우, 반드시 해당 도메인이 외부에 노출하는 유일한 통로인 **Facade**를 통해서만 접근하도록 강제한 것입니다.

> 💡 **규칙을 세운 이유**: 저희 프로젝트는 모놀리식 아키텍처이기에, 원한다면 얼마든지 외부 도메인에 직접 접근할 수 있었습니다. Facade 사용을 팀 규칙으로 강제함으로써 이러한 상황을 원천적으로 방지하고 설계 원칙을 지키고자 했습니다.

### 🎯 기대 효과
이러한 설계는 일반적인 모놀리식 애플리케이션이 겪는 다음과 같은 문제들을 방지하고 개선할 수 있었습니다.

- **높은 결합도(Coupling):** 한 도메인의 작은 변경이 연관된 다른 여러 도메인에 연쇄적인 수정을 유발합니다.
- **낮은 응집도(Cohesion):** 하나의 도메인이 자신의 책임 범위를 넘어 다른 도메인의 역할까지 침범하게 됩니다.
- **유지보수의 어려움:** 코드의 의존 관계를 파악하기 어려워지고, 새로운 기능을 추가하거나 기존 기능을 수정하게 되면 높은 결합도로 인해 마찬가지로 연쇄적인 수정이 발생합니다.

결론적으로 Facade 패턴은, 저희가 목표로 하는 “**MSA구조 모방하기”를 코드 레벨에서 실현**하는 핵심적인 전략입니다. 실제 MSA 환경에서는 각 도메인이 별도의 서버에 존재하며 HTTP 통신을 하지만, 저희는 **모놀리식 환경 속에서 Facade를 HTTP 통신의 역할로 간주**했습니다.
즉, 각 도메인을 독립된 서버처럼 취급하고 Facade라는 단일 API 창구를 통해서만 소통하게 함으로써, 프로젝트 전체의 유지보수성과 확장성을 크게 향상시킬 수 있었습니다.

## 2. 직접 정한 3개의 프로젝트 설계 원칙

우리 프로젝트에서는 Facade 패턴의 이점을 극대화하고, MSA 설계 사상을 성공적으로 적용하기 위해 다음과 같은 세 가지 구체적인 원칙을 반드시 준수합니다.

### 원칙 1: 🚪 도메인 간 직접 접근 금지

> 어떤 도메인도 다른 도메인의 서비스, 리포지토리, 엔티티를 직접 참조하거나 호출할 수 없다.
>

모든 도메인 간의 통신은 반드시 목표 도메인의 **Facade 인터페이스를 통해서만** 이루어져야 합니다.

- **잘못된 예시 ❌**: `MemberService`가 `ClubRepository`를 직접 주입받아 사용하는 경우
- **올바른 예시 ✅**: `MemberService`가 `ClubQueryFacade`를 주입받아 필요한 기능을 호출하는 경우

이 원칙을 통해 각 도메인의 내부는 외부로부터 완벽하게 보호되며, 이는 도메인 간의 결합을 끊어내는 가장 핵심적인 규칙입니다.

### 원칙 2: 🤝 엔티티 관계와 ID 필드의 공존: 현실적인 타협과 해결책

각 도메인을 완벽히 분리하기 위해서는 엔티티 간의 연관관계 매핑(`@ManyToOne` , `@OneToMany`등) 역시 제거하는 것이 이상적이었습니다. 하지만 이 경우, JPA가 자동으로 처리해주던 **트랜잭션 관리, N+1 문제 해결을 위한 `fetch join`, 영속성 전이(Cascade)** 등의 복잡한 매커니즘을 저희가 직접 구현해야 했습니다.

이는 현재 저희의 기술 수준과 개발 일정상 현실적으로 불가능한 목표라고 판단했습니다.

따라서 저희는 다음과 같은 현실적인 타협점을 찾았습니다.

> JPA의 연관관계 매핑은 그대로 사용하되, 코드 레벨에서는 연관된 객체에 대한 직접 참조를 팀 규칙으로 엄격히 금지한다.
>

그러나 이 규칙은 "연관된 객체의 ID를 어떻게 알 수 있는가?"라는 새로운 문제를 일으켰습니다. 객체에 직접 접근할 수 없으니, `bookStory.getMember().getId()` 와 같은 코드 또한 사용할 수 없게 된 것입니다.

저희는 이 문제를 **읽기 전용 ID 필드**를 추가하여 해결했습니다.

```java
@Entity
public class BookStory extends BaseEntity {

    // 실제 관계 매핑과 영속성 관리를 담당 (직접 접근 금지)
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "member_id")
    private Member member;

    // DB에 값을 쓰지는 않지만(insertable/updatable=false),
    // 연관 객체의 ID를 안전하게 조회하기 위한 읽기 전용 필드
    @Column(name = "member_id", insertable = false, updatable = false)
    private String memberId;
}
```

이 패턴을 통해 저희는 JPA의 강력한 기능은 그대로 활용하면서도, 코드상에서는 `bookStory.getMemberId()` 와 같이 **다른 도메인의 객체를 로딩하지 않고 필요한 외래 키 ID 값을 안전하게 조회**할 수 있게 되었습니다.

### 원칙 3: 📦 DTO를 통한 데이터 통신: 완전한 비종속성 구현

이렇게 얻어낸 ID를 통해 다른 도메인의 Facade에 정보를 요청하고, 그 결과를 받는 과정에서도 저희는 결합도를 낮추기 위한 원칙을 세웠습니다.

> 도메인의 경계를 넘나드는 모든 데이터는 반드시 특정 도메인에 종속되지 않는 공유 DTO(SharedDTO)여야 한다.
>

Facade 메서드의 반환 값으로 엔티티 객체를 직접 노출하는 것은 물론, 특정 도메인에 속한 `RequestDTO`나 `ResponseDTO`를 사용하는 것조차 내부 구조를 아는 것과 어느정도 일맥상통한다고 판단했습니다.

따라서 Facade는 항상 `global.dto` 패키지에 정의된 **공유 DTO** 형태로 데이터를 가공하여 반환해야 합니다. 이를 통해 각 도메인은 상대 도메인의 데이터 구조가 어떻게 생겼는지 전혀 알 필요 없이, 약속된 DTO 규격에만 의존하여 안전하게 통신할 수 있습니다. 이것이 저희가 구현한 **최종적인 도메인 간의 비종속성**입니다.
